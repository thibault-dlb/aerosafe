# API

This page describes the API as built: authentication, accounts, aircraft, flights, rules, alerts, replay, dashboard and collection. It starts with what the project sheet and the specifications require of it. The other error conventions are still `TBD`.

The API documentation is kept in the repository as Markdown and/or generated automatically (§VIII.2).

## Requirements

Source: project sheet §8 (a FastAPI API); specifications §II, §VI.1.1, §VII.1 and §III.2 for the role checks, the protection of endpoints and the 2-second target.

- The backend is a FastAPI application exposing business services and data.
- API endpoints check the caller's role before running a restricted operation.
- Stored data and API endpoints are protected (NF-02).
- Indicative performance target: a response in under 2 seconds on a standard search (NF-01).

## Authentication

Decided on 2026-11-03, see [technology choices](technology-choices.md#authentication).

- The API itself handles accounts: sign-up, login, logout and refresh. Passwords are hashed with argon2id.
- Login returns a short-lived access token (JWT, about 15 minutes) and sets a refresh token in an `HttpOnly` cookie. Only the hash of the refresh token is stored, so it can be revoked.
- Every request sends `Authorization: Bearer <access_token>`.
- The API checks the JWT signature and expiry.
- `get_current_user` reads the account on every request. The role checked by `require_role` comes from the database, so a role change or a deactivation applies at once. The `role` claim of the token is only informative.
- A missing, invalid or expired token returns 401. A valid token without the required role returns 403.
- Failed logins are throttled: 5 failures in 15 minutes for one e-mail from one address block that pair for 15 minutes (429). The counters live in memory, so they reset when the API restarts. Nginx sends the client address in `X-Forwarded-For`, overwriting any value the client sends, and uvicorn trusts it (`--proxy-headers`, with `FORWARDED_ALLOW_IPS`, `*` by default because the API port is not published: set it to the address of the gateway if you publish the port). The counter is therefore per e-mail and client address. Where Docker hides the real client address behind its own gateway address (Docker Desktop, for example), every local client may still share one counter.
- Deactivating or anonymising an account revokes its refresh tokens.
- The Swagger UI generated by FastAPI offers an Authorize button for testing.

| Item | Value |
| --- | --- |
| Access token | JWT signed with HS256 and `AUTH_JWT_SECRET` (at least 32 characters, not the `.env.example` value; the API refuses to start otherwise). Claims: `sub` (public ULID of the account), `role`, `iat`, `exp` |
| Access token lifetime | `AUTH_ACCESS_TOKEN_MINUTES`, 15 by default |
| Refresh token | Random value in the `refresh_token` cookie: `HttpOnly`, `SameSite=Strict`, path `/api/v1/auth`, `Secure` when `AUTH_COOKIE_SECURE=true`. Single use: each refresh revokes it and sets a new one. The check and the revocation are one `UPDATE`, so of two refreshes sent together with the same cookie only one succeeds; the other gets 401 and clears the cookie, so the front sends one refresh at a time |
| Refresh token lifetime | `AUTH_REFRESH_TOKEN_DAYS`, 7 by default |
| Passwords | 12 to 128 characters, no composition rule (OWASP), hashed with argon2id |
| Throttling | `AUTH_LOGIN_MAX_FAILURES` (5) and `AUTH_LOGIN_LOCK_MINUTES` (15) |

## Endpoints

Every work package has its router in `src/api/routes/v1/`, already included under `/api/v1`. Restricted endpoints use the `require_role` dependency of `core/security.py`. Each section below is completed by the owner of the router (see [team work split](team-split.md)).

### Authentication (`/api/v1/auth`)

No access token needed, except for `/auth/password`. E-mails are trimmed and lowercased.

| Method and path | Body | Success | Errors |
| --- | --- | --- | --- |
| `POST /auth/signup` | `{"email", "password"}` | 201, the account: `{"id", "email", "role", "is_active", "must_change_password"}`, role `USER` | 409 e-mail already registered, 422 invalid input |
| `POST /auth/login` | `{"email", "password"}` | 200, `{"access_token", "token_type": "bearer", "expires_in", "user"}`, and sets the refresh cookie | 401 wrong e-mail or password, or inactive account (same message), 429 too many failures |
| `POST /auth/refresh` | None, reads the refresh cookie | 200, same body as login, and sets a new refresh cookie | 401 missing, unknown, revoked or expired token; the cookie is cleared |
| `POST /auth/logout` | None, reads the refresh cookie | 204, revokes the token and clears the cookie | None |
| `POST /auth/password` | `{"current_password", "new_password"}`, with the access token | 200, same body as login: every session of the account is revoked and a new one opens; a provisional password stops being one | 400 wrong current password, 401 no valid token, 422 the new password is shorter than 12 characters or the same as the current one, 429 too many failures (the same limit as the login) |

`id` is always the public ULID, never the internal key. A default Supervisor account (`admin@aerosafe.com`) is created by the migrations, and other Supervisors are promoted with a command, see [installation](installation.md#installation).

### Accounts (`/api/v1/users`)

Work package `feat/auth-accounts` (BF-02, BF-14, UC-06, UC-09 to UC-11). Every endpoint answers 401 without a valid token. `id` is the public ULID.

An account created by a Supervisor starts with a **provisional password** (`must_change_password: true`). Until its owner replaces it with `POST /auth/password`, every endpoint of the API answers `403 {"detail": "Password change required"}`, except `GET /users/me`, `POST /users/me/anonymise` and `POST /auth/password`.

Supervisor only (403 for a User):

| Method and path | Body or query | Success | Errors |
| --- | --- | --- | --- |
| `GET /users` | `search` (part of the e-mail), `limit` (1 to 200, default 50), `offset` (0 to 10 000) | 200, `{"items": [account], "total"}`, oldest first, anonymised accounts included. An account: `{"id", "email", "role", "is_active", "must_change_password", "is_anonymised", "created_at"}` | 422 invalid query |
| `POST /users` | `{"email", "role"}`, role `USER` (default) or `SUPERVISOR` | 201, `{"account", "temporary_password"}`. The password is generated (four groups of five characters, without the ones that look alike), hashed at once and shown this once: the API keeps no copy | 409 e-mail already registered, 422 invalid input or role not available |
| `PATCH /users/{id}` | `{"role"?, "is_active"?}`, a missing field stays as it is | 200, the account. Deactivating revokes its sessions at once | 403 the caller's own account, 404 unknown, 409 anonymised account or last active Supervisor, 422 |
| `POST /users/{id}/anonymise` | None | 200, the account: e-mail `anonyme-<ULID>@aerosafe.invalid`, no password hash, inactive, sessions revoked | 403 the caller's own account, 404 unknown, 409 already anonymised or last active Supervisor |

Every authenticated account, with the provisional password too:

| Method and path | Body | Success | Errors |
| --- | --- | --- | --- |
| `GET /users/me` | None | 200, the account of the caller: `{"id", "email", "role", "is_active", "must_change_password"}` | 401 |
| `POST /users/me/anonymise` | `{"password"}` | 204, anonymises the account of the caller and clears the refresh cookie (the right to erasure, A-06) | 400 wrong password, 409 the caller is the last active Supervisor, 429 too many failures |

A Supervisor cannot change the role or the state of their own account, or anonymise it, from the list: the account page is where they leave. The last active Supervisor always stays: the API refuses to demote, deactivate or anonymise it. Every change is written to the audit log (`audit_logs`, table `UTILISATEUR`) with the old and new values of the role and the state; the e-mail address and the password are never written to it.

### Aircraft (`/api/v1/aircraft`)

Work package `feat/aircraft-lookup` (BF-04 to BF-07, UC-01). Every endpoint needs an authenticated caller, User or Supervisor; without a valid token it answers 401. Identifiers in paths and responses are the public ULIDs, never the internal keys.

| Method and path | Purpose | Answers |
| --- | --- | --- |
| `GET /aircraft` | Search aircraft | 200 with a list, possibly empty; 422 for invalid criteria |
| `GET /aircraft/preview` | Traffic of a live source, read from the source itself and stored nowhere | 200 with a list; 422 for `replay`; 503 when the source cannot be read now (with `Retry-After` when it announced a delay) |
| `GET /aircraft/{aircraft_id}` | Aircraft record | 200; 404 if unknown or deleted |
| `GET /aircraft/{aircraft_id}/observations` | Observation history | 200, oldest first; 404; 422 |
| `GET /aircraft/{aircraft_id}/flights` | Flights of the aircraft | 200, most recent first; 404 |

`GET /aircraft/preview?source=opensky|adsbfi` (default `adsbfi`) is for a dashboard whose instance does not collect the source: the API reads the aircraft of the area of the source on demand (the same area, client and account as the collection), and keeps the answer for one period of the source, whoever asks, so many open dashboards cost one request. Nothing is written to the database: the aircraft have no flight, no history and no alert, and their `id` is their ICAO24 address, so the other aircraft endpoints do not know them.

Query parameters of `GET /aircraft`. Every criterion is optional and they are combined (AND). Results are sorted by ICAO24 address.

| Parameter | Rule |
| --- | --- |
| `icao24` | Start of the address, 1 to 6 hexadecimal characters, case ignored |
| `registration` | Part of the registration, case ignored |
| `airline` | Part of the airline name or code, case ignored |
| `south`, `west`, `north`, `east` | Area in degrees (WGS 84), all four or none. It applies to the latest known position of each aircraft |
| `limit` | 1 to 2 000, default 50. The dashboard map asks for 2 000: it draws every aircraft of the area |
| `heard_within_seconds` | Live sources only, 1 to 3 600: keeps the aircraft heard in that many seconds before now, from a range of the index on the contact time. The dashboard map asks for 60 (or two periods of a slower source): adsb.fi gathers tens of thousands of aircraft a week, and the map shows the traffic of the moment |

Aircraft (search result and record):

```json
{
  "id": "01JC5Z8N0Q3V9X2K7M4T6B1R8D",
  "icao24": "3c6444",
  "registration": "D-AIBD",
  "model": "Airbus A319",
  "airline": "Lufthansa",
  "last_contact_at": "2026-11-09T10:00:00Z",
  "latitude": 48.85,
  "longitude": 2.35,
  "altitude": 10972.8,
  "heading": 284.0,
  "on_ground": false,
  "speed": 231.5
}
```

`model`, `airline` and `registration` are `null` when unknown; the last contact and the position are `null` when the aircraft never sent any. `altitude` (in metres), `heading` (degrees clockwise from north), `speed` (ground speed, in metres per second) and `on_ground` are those of the latest observation, and are `null` when the source did not send them or the aircraft was never observed. The map uses `heading` to turn the marker, `on_ground` to draw a grounded aircraft as a diamond, and `heading` with `speed` to carry the aircraft forward between two reports and to draw its line of the next 15 minutes.

`GET /aircraft/{aircraft_id}/observations` takes `start` and `end` (ISO 8601, inclusive, both optional; `start` must not be after `end`) and `limit` (1 to 5 000, default 500). It returns the latest `limit` observations of the period, in chronological order:

```json
{
  "last_contact_at": "2026-11-09T10:00:00Z",
  "position_at": "2026-11-09T09:59:58Z",
  "latitude": 48.85,
  "longitude": 2.35,
  "altitude": 10000.0,
  "speed": 230.5,
  "heading": 90.0,
  "on_ground": false,
  "flight_id": "01JC5Z9A2B3C4D5E6F7G8H9J0K"
}
```

Units: altitude in metres, speed in metres per second, heading in degrees clockwise from north. Any measured value is `null` when the source did not send it; `flight_id` is `null` for an observation that belongs to no flight.

`GET /aircraft/{aircraft_id}/flights` takes `limit` (1 to 200, default 50) and returns flight summaries, described below.

### Flights (`/api/v1/flights`)

Work package `feat/aircraft-lookup` (BF-07, BF-08, UC-02). Users and Supervisors can both view trajectories (team decision C-06).

| Method and path | Purpose | Answers |
| --- | --- | --- |
| `GET /flights/{flight_id}` | Trajectory, missing segments and statistics of a flight | 200; 404 if unknown or deleted; 401 |

Flight summary, also returned by `GET /aircraft/{aircraft_id}/flights`:

```json
{
  "id": "01JC5Z9A2B3C4D5E6F7G8H9J0K",
  "aircraft_id": "01JC5Z8N0Q3V9X2K7M4T6B1R8D",
  "icao24": "3c6444",
  "registration": "D-AIBD",
  "callsign": "DLH4AB",
  "started_at": "2026-11-09T09:00:00Z",
  "ended_at": null,
  "origin": "Frankfurt",
  "destination": null
}
```

`ended_at` is `null` while the flight goes on. `GET /flights/{flight_id}` adds:

- `trajectory`: the observations of the flight, oldest first, in the format above (at most 10 000);
- `gaps`: the missing segments, `{"start", "end", "duration_seconds"}`. Two consecutive positions more than 300 seconds apart are not joined, which is the upper bound of the window of rules R3 to R5. The partial trajectory is still returned (UC-02, alternative flow 2a);
- `statistics`: `observation_count`, `duration_seconds` (first to last observation), `distance_km` (great-circle length, gaps excluded), `mean_altitude` and `max_altitude` in metres, `mean_speed` and `max_speed` in metres per second. A mean or maximum is `null` when no observation has the value.

### Rules (`/api/v1/rules`)

Work package `feat/rules-alerts` (BF-13, UC-05). Every endpoint needs the Supervisor role (401 without a token, 403 with another role). A rule is identified by its code.

| Method and path | Purpose | Answers |
| --- | --- | --- |
| `GET /rules` | Every rule with its settings, sorted by code | 200 |
| `GET /rules/{code}` | One rule | 200; 404 if unknown |
| `PATCH /rules/{code}` | Change the threshold, the activation or the criticality | 200 with the rule; 404; 422 for an invalid value or an unknown field |

A rule:

```json
{
  "code": "R1",
  "description": "Délai trop long depuis le dernier contact",
  "threshold": 300.0,
  "unit": "s",
  "criticality": "MEDIUM",
  "is_active": true,
  "updated_at": "2026-11-09T10:00:00Z"
}
```

Body of `PATCH /rules/{code}`. Every field is optional, and a missing field keeps its value:

| Field | Rule |
| --- | --- |
| `threshold` | Number from 0 to 9 999 999.999, in the unit of the rule |
| `is_active` | `false` stops the evaluation of the rule; the next evaluation ends its open episodes |
| `criticality` | `LOW`, `MEDIUM`, `HIGH`, or `null` to remove it; 422 if the level is disabled in `R_CRITICITE`. It is copied into the alerts raised afterwards |

The engine reads the rules on every evaluation, so a change applies at the next one. Alerts already raised keep the threshold in force when they were triggered. Every change is written to `audit_logs` with the old values, the new values and the Supervisor.

### Alerts (`/api/v1/alerts`)

Work package `feat/rules-alerts` (BF-10, BF-12, UC-03, UC-04). Every endpoint needs the Supervisor role (401 without a token, 403 with another role). Identifiers are public ULIDs.

| Method and path | Purpose | Answers |
| --- | --- | --- |
| `GET /alerts` | Alerts matching the filters, sorted, one page at a time | 200 with `{"items", "total"}`; 422 for invalid criteria |
| `GET /alerts/statistics` | Number of alerts per rule over a period | 200; 422 if the start is after the end |
| `GET /alerts/{alert_id}` | Details of one alert | 200; 404 if unknown or deleted |
| `POST /alerts/{alert_id}/process` | Mark the alert as processed by the caller | 200 with the alert; 404; 409 if already processed |

Query parameters of `GET /alerts`. Every criterion is optional and they are combined (AND). `total` counts every alert that matches, all pages included. It is an exact count, run with each page: filtered through indexed columns on a table of a few thousand rows, it stays cheap, and the page needs it for its navigation.

| Parameter | Rule |
| --- | --- |
| `rule` | Code of the rule, such as `R3` |
| `status` | `active` (the situation still lasts), `unprocessed` or `processed` |
| `criticality` | `LOW`, `MEDIUM` or `HIGH` |
| `icao24` | Start of the address, 1 to 6 hexadecimal characters, case ignored |
| `start`, `end` | Trigger time, inclusive bounds (ISO 8601 with a time zone, such as `Z`; 422 without one) |
| `sort` | `triggered_at` (default), `criticality` or `rule`. Ties are sorted by trigger time, the latest first |
| `order` | `desc` (default) or `asc` |
| `limit` | 1 to 200, default 50 |
| `offset` | 0 to 10 000, default 0. OFFSET paging reads every skipped row, so it is bounded; narrow the period or the filters to reach older alerts |

An alert:

```json
{
  "id": "01JC5ZB0K8M2N4P6Q8R0S2T4V6",
  "aircraft_id": "01JC5Z8N0Q3V9X2K7M4T6B1R8D",
  "icao24": "3c6444",
  "registration": "D-AIBD",
  "rule_code": "R3",
  "rule_description": "Variation importante d'altitude",
  "triggered_at": "2026-11-09T10:00:00Z",
  "episode_ended_at": null,
  "observed_value": -40.0,
  "threshold": 30.0,
  "unit": "m/s",
  "message": "R3 vertical rate for 3c6444: -40.0 m/s beyond the threshold of ±30 m/s",
  "criticality": "HIGH",
  "processed_at": null
}
```

- `triggered_at` is the time of the collection that triggered the rule, not the time the engine ran.
- `episode_ended_at` is `null` while the situation lasts. The aircraft raises no new alert for the same rule until then (see [business rules](business-rules.md#scope-and-deduplication)).
- `processed_at` is `null` until a Supervisor marks the alert as processed. The Supervisor is stored but not returned.

`GET /alerts/statistics?start=&end=` returns `{"start", "end", "total", "per_rule": {"R1": 4, "R3": 1}}`. Both bounds are optional and need a time zone: `end` defaults to now and `start` to 24 hours before `end`. Rules without alerts in the period are absent from `per_rule`. The dashboard reads the same counts through `AlertService.statistics()`.

### Replay (`/api/v1/replay`)

The replay of the historical traffic (D-20, see [historical data](historical-data.md#replay-mode)). The clock is shared: what a Supervisor starts, pauses or speeds up, every user sees. Instants are UTC and need a time zone.

| Method and path | Role | Purpose | Answer |
| --- | --- | --- | --- |
| `GET /replay` | any authenticated user | The period of the replayed data and the clock: `available`, `start`, `end`, `simulated_at` (null before the first start), `speed`, `paused`, `finished`, `server_time` (the real instant of the reading, so a client can move `simulated_at` itself between two readings) and `allowed_speeds` | `200` |
| `POST /replay/start` `{"at", "speed"}` | Supervisor | Starts at `at`, inside the period, even when a replay is running: the alerts of the earlier run dated `at` or later are removed (logically) and the open episodes end at `at` | `200` with the clock, `409` when no replayed data is imported, `422` for an instant outside the period, a date without time zone or a speed that is not allowed |
| `POST /replay/pause`, `POST /replay/resume` | Supervisor | Freezes or resumes the simulated time | `200`, `409` before the first start |
| `POST /replay/speed` `{"speed"}` | Supervisor | Changes the speed from the time reached; the speeds are 1, 10 and 60 | `200`, `409` before the first start, `422` for another speed |

The clock stops at the end of the data. It is stored in `PARAMETRE_REJEU` (a start moves nothing while it runs: the simulated time is the instant at the last change plus the real time gone by times the speed), so it survives a restart of the API. A scheduler reads it every 10 s and runs the rules engine for each 30 s step of simulated time that went by, at most 120 steps a tick.

`source` on `GET /aircraft`, `/aircraft/{id}`, `/aircraft/{id}/observations`, `/aircraft/{id}/flights`, `/flights/{id}`, `/alerts`, `/alerts/statistics` and the dashboard picks the data: `opensky` (the default when the parameter is absent) or `adsbfi` for one of the two live collections, `replay` for the historical traffic. Each source has its own aircraft, flights, observations and alerts (D-23): an aircraft heard by both live sources has one record in each. The interface always sends the source shown, adsb.fi by default. The former value `live` is refused (422).

`source=replay` reads the replayed traffic at the simulated instant:

- the aircraft search lists the aircraft heard in the minute before it, with their position then; the record gives the latest position up to it;
- the observation history, the flights and the trajectory stop at it (a flight that ends after it is still in progress, one that starts after it does not exist yet);
- the alerts are those of the replayed aircraft triggered up to it, and the statistics default to the 24 hours before it;
- a replay that was never started has no instant, so the search and the alerts are empty.

### Dashboard (`/api/v1/dashboard`)

Work package `feat/dashboard` (BF-11, UC-04, team decision A-04). **Every account** reads the dashboard, a User as well as a Supervisor: 401 without a token, 403 while the password is a provisional one. It changes nothing; the actions behind it (processing an alert, pausing the collection) stay the Supervisor's, on their own routes. The service reads through `AlertService` and `CollectionStateStore`, never the tables. The alerts are those of the source asked; with `source=replay`, those of the replayed traffic up to the simulated instant, and a replay that was never started has no alert. The collection state is the one of the live source shown, and of adsb.fi during a replay.

| Method and path | Query | Success | Errors |
| --- | --- | --- | --- |
| `GET /dashboard` | `source` (`opensky`, `adsbfi` or `replay`) | 200, `{"counters": {"active_alerts", "unprocessed_alerts", "alerts_24h"}, "active_alerts": [alert], "alerted_aircraft": [alert], "collection": {...}}`. `active_alerts` holds the 5 latest alerts whose situation lasts (same body as in [Alerts](#alerts)); `alerted_aircraft` holds, for each aircraft with an active alert (up to 500 alerts read), its most critical one: the map colours these aircraft and the card of the followed aircraft shows its alert; `alerts_24h` counts the 24 hours before now, or before the simulated instant | 401 |
| `GET /dashboard/statistics` | `period` (`24h` default, `7d`, `30d`), `source` | 200, `{"period", "unit", "start", "end", "total", "slices": [{"start", "total", "per_rule": {"R1": 2}}]}`. 24 slices of one hour for `24h`, 7 or 30 of one day otherwise, the last one being the current hour or day (UTC). The slices without alert are present, with a total of 0 | 401, 422 unknown period |

`collection` is a summary the User may read: `{"source", "period_seconds", "area", "enabled", "paused", "running", "last_success_at", "remaining_credits", "recent_runs": [{"started_at", "status"}]}`, the 12 latest runs, newest first. `period_seconds` is the pace of the collection, which the map follows; `area` holds the rectangle that contains the area of the source (`south`, `west`, `north`, `east`), which the map frames, and for adsb.fi the centre and radius of its circle (`latitude`, `longitude`, `radius_km`, `null` for OpenSky), which the map draws. `remaining_credits` is always `null` for adsb.fi. It carries no error text; the Supervisor's `GET /collection/status` has the detail.

The map of the dashboard is not part of this answer: it reads the aircraft of the area with `GET /aircraft`.

### Collection (`/api/v1/collection`)

Every endpoint needs the Supervisor role (401 without a token, 403 with another role) and takes `source=opensky` (the default) or `source=adsbfi`: the two live collections run in parallel, each with its own runs, pause and wait after a 429 (`replay` is refused, 422). Run times are UTC.

| Method and path | Purpose | Answer |
| --- | --- | --- |
| `GET /collection/status` | State of the collection of the source: `source`, enabled on this instance, paused, cycle running, profile, period, credits per day and daily quota, anonymous or authenticated access (`daily_quota` and `authenticated` are `null` for adsb.fi, which has no account), wait after a 429, last run and last successful run | `200` |
| `GET /collection/runs?limit=20&before=<started_at>` | Latest runs, newest first. `limit` from 1 to 100. For the next page, `before` is the `started_at` of the last run received (keyset paging: cycles never overlap, so `started_at` is unique) | `200`, `422` if out of range |
| `POST /collection/run` | Runs one cycle of the source now and returns it, even when its collection is paused. With OpenSky it uses credits | `200`, `409` when the collection of the source is disabled on this instance, a cycle of it is already running, or the source answered 429 (or refused a request, for adsb.fi) and its delay is not over |
| `POST /collection/pause` | Suspends the periodic collection, without stopping the API. Later cycles are recorded as `SKIPPED` | `200` with the status |
| `POST /collection/resume` | Resumes the periodic collection | `200` with the status |

A run has `source`, `started_at` (also the `now` given to the rules engine), `ended_at`, `status` (`SUCCESS`, `PARTIAL` when some state vectors were rejected, `FAILED`, `RATE_LIMITED` for a 429 and for the cycles during its delay, `SKIPPED` while paused), `profile`, `received`, `stored` (new observations), `rejected`, `remaining_credits` (from OpenSky, `null` for adsb.fi), `error` and `evaluation_error` (a failure of the rules engine, which never cancels the collection).

Each run is written once to `EXECUTION_COLLECTE`, complete, with its source and its end set after the rules evaluation. The pause of each source is kept in its row of `PARAMETRE_COLLECTE`, so it survives a restart of the API.

Configuration, in `.env`:

| Variable | Default | Meaning |
| --- | --- | --- |
| `COLLECTION_OPENSKY_ENABLED` | `false` | Whether this instance collects OpenSky. Only one instance collects with the group account at a time |
| `COLLECTION_PROFILE` | `ILE_DE_FRANCE` | OpenSky profile: `ILE_DE_FRANCE` (every 30 s) or `FRANCE` (every 120 s), see [architecture](architecture.md#data-source) |
| `COLLECTION_FLIGHT_GAP_MINUTES` | `30` | Maximum gap between two observations of the same flight, for both sources (D-06) |
| `COLLECTION_BBOX_ILE_DE_FRANCE`, `COLLECTION_BBOX_FRANCE` | see [OpenSky Network](opensky.md#collection) | OpenSky areas, as `lat_min,lat_max,lon_min,lon_max` |
| `OPENSKY_CLIENT_ID`, `OPENSKY_CLIENT_SECRET` | empty | OAuth2 API client of the group account; empty means anonymous access |
| `COLLECTION_ADSBFI_ENABLED` | `false` | Whether this instance collects adsb.fi. adsb.fi needs no account |
| `ADSBFI_CENTER`, `ADSBFI_RADIUS_NM` | `48.65,2.5`, `250` | Circle collected from adsb.fi: its centre (`lat,lon`, the middle of the Île-de-France box) and its radius in nautical miles, 250 at most |
| `ADSBFI_PERIOD_SECONDS` | `5` | Period of the adsb.fi collection, 2 s at least (one request per second at most) |
| `ADSBFI_TIMEOUT_SECONDS` | `4` | Time allowed to an adsb.fi answer, shorter than the period |
| `ADSBFI_RETENTION_DAYS` | `7` | Days of adsb.fi observations kept; older ones are deleted every hour. `0` keeps everything |
| `RULES_EDGE_MARGIN_KM` | `20` | R1 and R2 say nothing about an aircraft last placed closer than this to the edge of the area of its source (D-23) |

The API refuses to start when the OpenSky profile would use more than the 4 000 daily credits of an account, or when the adsb.fi settings are out of bounds. With anonymous access the OpenSky credits run out after a few hours; OpenSky then answers 429 and the collection waits for the delay it announces. adsb.fi answers 429 when requests come too fast, and counts the refused requests (400, 401, 403, 404) against its limit: after either, the adsb.fi collection waits the announced delay, a minute without one. See [data sources](data-sources.md).
